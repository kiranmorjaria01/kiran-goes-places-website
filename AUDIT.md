# Kiran Goes Places — GEO/AEO Audit (Phase 0)

Audit date: 2026-08-18. No code was changed to produce this document. All figures below were generated by inspecting the repository directly (`/Users/kiran/kiran-goes-places-website`), not by crawling the live site, so anything DNS/CDN/Netlify-level (redirects, headers, actual served robots.txt) should be spot-checked against production before Phase 1 ships.

---

## 1. Stack, build process, templating, metadata injection

- **Stack:** plain static HTML/CSS/JS. No framework, no static site generator, no build step. `find` turns up no `package.json`, no generator/template scripts anywhere in the repo — the only JS file is `js/main.js` (progressive-enhancement behaviour: sticky nav, mobile menu, fade-ins, YouTube facade swap, Formspree contact form). One shared stylesheet, `css/style.css`.
- **Templating: there is none.** Every page — `index.html`, `blog/index.html`, and each of the 50 `blog/<slug>/index.html` files — is a standalone, hand-duplicated HTML document. The `<head>`, nav, and footer markup is copy-pasted into all 52 files independently.
- **Metadata injection:** all metadata (title, meta description, canonical, OG tags, JSON-LD) is written directly and statically into each file's `<head>`. Nothing is templated or generated at build/request time.
- **Practical implication for Phases 1-7:** because there is no shared include/partial mechanism, any change that touches every page (sitemap regen aside) means either scripted find/replace across 50+ files or 50+ individual edits. Worth deciding up front whether to introduce a lightweight build step (even just a Python/Node script that stitches head/nav/footer partials into static output at commit time) versus continuing to hand-edit. Flagging this now since it affects how Phases 2-7 should actually be executed, not just what they produce.

## 4. JSON-LD inventory

**Correction to the brief's expectation: it is not zero.** There is JSON-LD already on the site, though it's thin and inconsistent:

- **Homepage (`index.html`):** one `Person` block — `name: "Kiran Goes Places"`, `alternateName: "Kiran Morjaria"`, nationality, homeLocation, knowsAbout, affiliation (BBC), and `sameAs` (Instagram, YouTube, TikTok only — no kiranmorjaria.com, no BBC/TEDx/Channel 5 profile links, no LinkedIn). No `@id`, so nothing else on the site can reference this node.
- **Every one of the 50 blog posts:** a minimal `BlogPosting` block — `headline`, `datePublished`, inline `author` (`Person`, name only, no `@id`, no link to the homepage Person node), `image`, inline `publisher` (`Organization`, name only, no logo, no `sameAs`). No `dateModified`, no `mainEntityOfPage`, no `description`.
- **`blog/index.html` (the listing page):** no JSON-LD at all.
- **Missing entirely, site-wide:** `Organization` as its own referenceable node, `VideoObject`, `FAQPage` (despite a five-question FAQ block already live on the homepage, marked up as plain `<details>` with no schema), `BreadcrumbList`, `ItemList` (despite at least 10 listicle-style posts — Tokyo 20 Things, Mount Fuji 7 viewpoints, several Guatemala/Colombia "top things to do" posts — that are exactly the ItemList use case).

So Phase 2 isn't starting from a blank slate: it's replacing/extending 50+ thin, disconnected `BlogPosting` blocks and one orphaned `Person` block with a proper linked graph (stable `@id`s, `Person` ↔ `Organization` ↔ `BlogPosting` cross-references), on top of adding the schema types that don't exist yet.

## 5. Video embedding

- **Not a naive iframe embed and not self-hosted.** Every video (homepage showreel, blog post embeds, the homepage shorts coverflow) uses the same pattern: a static `<button class="guide-play" data-video-id="...">` showing a poster image, with a sibling `<div class="guide-embed" hidden>` containing an `<iframe>` whose `src` is empty and the real URL sits in `data-src`. `js/main.js` swaps `data-src` into `src` only on click. This is a genuine lazy-loaded facade (good for performance, and it means no iframe network request fires until a user acts) built on `youtube-nocookie.com/embed` (privacy-conscious YouTube embeds, not self-hosted video).
- **No transcript text anywhere.** Confirmed: zero matches for "transcript" across all 50 blog post files. Zero chapter/timestamp markup either (the one "chapter" hit found by a keyword search is prose — "a genuinely dark chapter of the city's history" — not a video chapter list).
- **Practical note for Phase 6:** because the iframe `src` is empty until a click, and there's no transcript text in the DOM regardless, the video content is currently 100% invisible to any retrieval system, crawler or human reading view-source. This is the single clearest "currently invisible" finding in this audit and matches the brief's framing exactly.

## 6. Server-rendered vs JS-injected content

**Confirmed server-rendered.** Every blog post's full article body — headline, subheading, byline, all paragraph text, all image tags with real `src`/`alt`, captions — is present as static markup in the HTML file itself, not injected by JavaScript. I read `js/main.js` in full: its only DOM-writing behaviours are nav show/hide on scroll, mobile menu toggle, fade-in-on-scroll class toggling, the video-embed click-to-load swap described above, a contact-form AJAX submit handler, and setting the footer copyright year. None of it writes article content. Viewing any post with JavaScript disabled would render the complete text, all images, and the FAQ block on the homepage (native `<details>`/`<summary>`, which works with no JS at all). The only things a JS-disabled visitor loses are the click-to-play video swap (they'd see a static poster button instead of a playable video) and the animation/nav-hide flourishes.

This is good news: it means "nothing else in this brief matters until it's true" (per Phase 1) is already true, and Phase 1's JS-disabled check should be a fast confirmation pass rather than a fix.

## Additional items worth flagging before Phase 1 (per the brief's instruction to raise rather than ship)

- **`llms.txt` already exists** at the repo root (`llms.txt`, last touched 14 Jul). The brief says not to add one and to raise the case instead if I think there's one — since one is already shipped, the live decision is keep vs remove, not add vs don't. It's short (bio, travel history, booking info, links) and costs nothing to serve, but per the brief's own reasoning (weak evidence, Google has confirmed no effect) it isn't doing any retrieval work either. My recommendation: leave it as-is — it's harmless, small, and plausibly useful as a human-readable one-pager for any agent that does choose to fetch it — but don't invest further in it, and don't treat it as a substitute for anything in Phases 1-7. Flagging for your sign-off rather than touching it.
- **JSON-LD already exists**, contrary to the brief's stated expectation of zero — see item 4. This changes Phase 2 from "add from scratch" to "replace/extend a thin, disconnected implementation," which is more file-touching than a from-scratch add would be (50 existing `<script type="application/ld+json">` blocks to revise, not insert fresh).
- **No CMS/build step** (item 1) means every phase that touches all 50+ posts is a scripted bulk-edit against flat HTML files, not a template change. Worth agreeing the edit approach (scripted regex/DOM patch vs per-file) before Phase 2 starts, since it affects review-ability of the "one phase per commit" deliverable.
- **Sitemap gap:** the newest post (Suzuka F1, 2026-07-15) is missing from `sitemap.xml` right now, independent of anything else in this brief — worth fixing as the first line of Phase 1.
